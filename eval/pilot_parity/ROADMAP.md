# 自作チェッカーを Pilot と同じ水準に引き上げる計画（P4、2026-10-15）

研究の問い「自作 SysML v2 Checker は Pilot 実装（0.62.0）と同じ水準に到達できるか」に答えるための、到達目標・段階・優先順位・見積もり。根拠は `BASELINE.md`（P2 / P3）と `analyze_gaps.py` の集計（`results/latest/gaps.json`）。

## 1. 「同じ水準」の定義（到達判定の基準）

コーパス（現在 519 件。段階 B で KerML の名前解決のテスト 105 件を加えた。Pilot のバージョンが上がったら作り直す）で、次をすべて満たしたら「到達」とする。

| 基準 | 目標 | P3 時点 | 段階 A 後 | 段階 B 後 | 段階 C 後 | 段階 D 後 |
| --- | --- | --- | --- | --- | --- | --- |
| 正しいモデルを誤りとしない（verified + xpect の valid） | 0 件 | 4 件（verified 4 / 5） | **0 件** | **0 件** | **0 件** | **0 件** |
| unit 単位の見逃し（Pilot はエラー、自作は問題なし） | ≤ 2% | 25.9% | 38.6%（見かけの悪化。`BASELINE.md` の段階 A を参照） | 8.7% | 6.3% | 5.7% |
| 行 + 種類の再現率 / 適合率 | ≥ 90% / ≥ 90% | 15.2% / 23.1% | 16.4% / 67.1% | 51.4% / 84.7% | 70.5% / 87.0% | 74.8% / 88.4%（構文エラーの無い unit で **92.0% / 97.2%**） |

（P3 時点で「xpect valid 1 / 34」としていた 1 件は、Pilot も同じエラーを出すテストで、誤検出ではなかった。）

「種類」での一致にとどめるのは、自作のメッセージが日本語で Pilot と文言が違うため。到達の最終確認では、各指摘に Pilot の英語メッセージ（`pilot_message`）を持たせ、**メッセージ単位**でも測る（段階 D）。

## 2. 差の在りか（Pilot の層ごと）

| 層 | Pilot のエラー | 自作の一致 | 再現率 | Pilot 側の主な実装（規模） |
| --- | --- | --- | --- | --- |
| 1 文法 | 181 | 114 | 63% | Xtext 文法（約 4.9 千行）。自作はほぼ追従済み |
| 2 名前解決（未解決参照・アクセス範囲） | 525 | 41 | 7.8% | scoping（1.1 千行）＋ 派生プロパティ（継承・import・可視性、17.8 千行の一部） |
| 3 種類の判定（解決結果の種類を使う） | 399 | 14 | 3.5% | `@Check` のうち「X must be typed by Y definitions」系 26 メッセージ、`Must reference a …`、concrete type |
| 4 個別の検証ルール | 118 | 48 | 41% | `@Check` 115 個・メッセージ 186 種類（約 3 千行） |

**差のほぼすべてが層 2 と 3 にある**（LLM に近い入力での取りこぼし 848 件のうち 744 件）。層 3 は層 2 の結果（参照先が何の種類か）を使うだけなので、本体は層 2。

### 層 2 が弱い理由（コードで確認）

自作の型解決（`linter.py` の `_find_type_in_symbols`）は、ファイル全体の **平らな名前表**を引く。

- どこかに同じ短い名前の定義があれば、スコープ・import・可視性に関係なく「解決できた」とみなす。
- `Real` などの組み込み型は import しなくても常に見える → import 漏れを検出できない（変異体で 1 / 10）。
- 継承（`:>`・型付け）で入ってくるメンバー、`::` と `.` の区別（フィーチャか名前空間か）を持たない（1 / 13）。
- 単位（`[kN]` など）の存在を見ていない（0 / 12）。

一方、**標準ライブラリの索引（`library_index.json`、98 パッケージ、要素ごとの種類つき）は既にある**。層 2 を作り直すときの土台になる。

## 3. 段階・優先順位・見積もり

LLM の誤りに近い入力（llm・mutant・probe）での「取りこぼし件数」の多い順に並べた。見積もりは、Claude と一緒に作業する 1 人での目安（不確実性が大きい。段階ごとにこのハーネスで測って見直す）。

| 段階 | 内容 | 取りこぼしの規模（LLM 系） | 見積もり | 終了条件 |
| --- | --- | --- | --- | --- |
| **A 文法の穴とパース停止** | (1) state def の中の `port`（22 件に波及）、`default :=`（25 件）、`perform action x ::> y` を受け付ける (2) import の可視性を必須にする（公式文法どおり） (3) パースエラーがあっても、読めた部分は lint する | 構文 66 件 ＋ パース停止で止まっている全ルール | 小（1 週間） | 正しいモデルの誤検出 0、構文の再現率 ≥ 90% |
| **B スコープつき名前解決** | 名前空間の木、所有メンバー、import（private / public、`::*`、`::**`、要素 import）、可視性、特化・型付けによる継承メンバー、ライブラリ索引の拡張（継承メンバー・可視性・フィーチャ／定義の別）。単位の解決もここで入る | 未解決参照 409 件 ＋ アクセス範囲 41 件 | 大（4〜6 週間） | 未解決参照・アクセス範囲の再現率と適合率 ≥ 90% |
| **C 解決結果を使う種類の判定** | 「X must be typed by Y definitions」系 26 メッセージを、(使用の種類 → 許される定義の種類) の表で一括実装。`Must reference a …`、concrete type、model-level evaluable | 型の種類 253 件 ＋ Must reference 36 件 ＋ その他 5 件 | 中（2〜3 週間） | 種類の判定の再現率 ≥ 90% |
| **D 残りの検証ルール** | Pilot の検証メッセージ 186 種類を一覧（`analyze_gaps.py` の messages）にして 1 つずつ対応づける。再定義の制約（nonunique・方向・所有型）、束縛の上書き、関係の数など。各指摘に `pilot_message` を持たせる | 個別ルール 約 40 件 ＋ コーパスに未出現の約 120 メッセージ | 中〜大（3〜4 週間） | xpect の期待エラー ≥ 95%、メッセージ単位でも測る |
| **E 追従** | Pilot の新しい版ごとにコーパスを作り直して測り、差分を取り込む。版ごとにベースラインを分けて残す | — | 継続 | 版ごとの到達判定 |

合計の目安は **2.5〜3.5 か月**。段階 B の出来がほぼ全体を決める（研究としての答えも B で決まる）。

### 段階 B の進め方（オラクルの使い方）

- **コードではなくデータをオラクルから取る**: ライブラリの継承メンバー・可視性・要素の種類は、Pilot（sysml-mcp-server の `outline_sysml` / `lookup_sysml` と同じ常駐デーモン）にライブラリを評価させて書き出し、索引を作り直す。Pilot のロジックを手で写さずに済む部分は写さない。
- **解決の規則は小さな単体テストで固める**: import の種類 × 可視性 × 継承の組み合わせを、xpect の `visibility` / `imports` / `scoping` テスト（KerML 側、約 90 件）と、P1 の負例から作る。KerML 側のテストは現在コーパスに入れていないので、段階 B の開始時に加える。
- **分からないときは「不明」を返す**: 解決できない形（式の中の複雑なフィーチャ連鎖など）は、誤ったエラーも誤った「問題なし」も出さず「検証不能」とする。到達判定では「不明」も取りこぼしとして数え、隠さない。

## 4. 研究としての見通し

- 層 1（文法）と層 4（数え上げで判定できる規則）は、既に到達しているか、短期間で到達できる。
- 層 2・3 は KerML の名前解決の再実装そのもので、Pilot 側でも約 2 万行規模の中核。オラクルからデータを取ることで量は減らせるが、**規則の再実装は避けられない**。
- したがって「Pilot と同じ水準に到達できるか」の答えは、段階 B の終了時点で、名前解決の再現率・適合率が 90% に届くかで判定するのが妥当。届けば残り（C・D）は表と個別ルールの作業で、到達の見通しが立つ。

## 5. 次の一手

段階 A は終了条件を満たした（2026-10-15）: 正しいモデルの誤検出 0、構文の再現率 90%（unit ごとの最初の構文エラー、63 / 70）。詳細は `BASELINE.md` の段階 A。残りの構文 7 件（自作の文法が Pilot より緩い形）は段階 D で個別に扱う。

段階 B（スコープつき名前解決）は終了条件を満たした（2026-10-16）: Pilot に構文エラーの無い unit で、未解決参照の再現率 90.3%・適合率 98.1%、アクセス範囲の再現率 95.3%・適合率 100%、正しいモデルの誤検出 0。層 2 の再現率は 7.8% → 74.8%、見逃し率は 25.9%（P3）→ 8.7%、変異体の検出は 98%。詳細と残した課題は `BASELINE.md` の段階 B。

**研究としての答え（段階 B の時点）**: 名前解決は、データ（ライブラリの索引と、定義の本体で宣言される名前）と約 1,100 行の規則（`scope_resolver.py`）で、Pilot に構文エラーの無い入力では 9 割を超えて再現できた。ROADMAP の 4 章で「答えは段階 B で決まる」とした点については、**到達できる見通しが立った**と判断する。残る差は層 3（解決結果の種類を使う判定、再現率 13%）と層 4（個別の検証ルール、41%）で、どちらも名前解決の結果を使う表と個別ルールの作業になる。

段階 C（解決結果を使う種類の判定）は終了条件を満たした（2026-10-16）: Pilot に構文エラーの無い unit で、種類の判定の再現率 95.1%・適合率 99.2%、参照先の種類の再現率 93.3%・適合率 100%。参照実装の checkAllTypes / checkOneType を、名前解決の結果と KerML のメタクラスの表で写した（約 400 行）。見逃し率は 6.3%、行 + 種類の再現率 70.5%・適合率 87.0%、xpect の期待エラーは 110 / 164。型が未解決のときに参照実装が重ねて出す種類のエラーは、連鎖として数える（`BASELINE.md` の段階 C）。

段階 D（個別の検証ルール）は終了条件を満たした（2026-10-16）: Pilot に構文エラーの無い unit で行 + 種類の再現率 92.0%・適合率 97.2%、xpect は Pilot 自身が同じ箇所に出す期待エラーのうち 95.5%（基準の読み替えは `BASELINE.md` の段階 D）、正しいモデルの誤検出 0。

**研究としての答え（段階 D の時点）**: Pilot に構文エラーの無い入力について、自作チェッカーは Pilot の判定を行 + 種類の単位で 9 割以上（再現率 92%・適合率 97%）再現し、正しいモデルを誤りとしない。名前解決（段階 B）・種類の判定（段階 C）・個別ルール（段階 D）のいずれも、参照実装のロジックを読んで写し、オラクルとの差分で境界を確かめる方法で到達できた。**「Pilot と同じ水準に到達できるか」には、開発コーパスの構文エラーの無い入力については「できる」と答えられる**。ただし開発に使っていない公開モデル（held-out）では、再現率は 81% まで汎化したものの、正しいモデルの誤検出が 96 件中 17 → 27 件に増えた（名前解決と文法の個別の不足。研究の結果のまとめは `RESULTS.md`）。到達していないのは、(1) Pilot に構文エラーがある入力（Pilot のエラー回復で要素が消えた先の連鎖エラーまで真似ていない）、(2) unit 単位の見逃し率（目標 2% に対し 5.7%。見逃し 17 件のうち 12 件は Pilot に構文エラーの無い unit で、束縛の上書き 4 件など未実装の個別ルール。残り 5 件が (1)）。

次は段階 E（追従）。Pilot の新しい版ごとにコーパスを作り直して測る。研究としては、(1) の扱い（エラー回復の真似をするか、到達判定から外すか）を決めて、結果をまとめる。
